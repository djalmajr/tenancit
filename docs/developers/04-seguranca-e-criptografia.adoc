=== Segurança e criptografia

==== Fronteiras de autenticação

Há duas fronteiras independentes:

[cols="1,2,2",options="header"]
|===
| Superfície | Credencial | Propósito

| `/v1/admin/*`
| Sessão OIDC opaca + CSRF/origin; bearer somente para break-glass explícito
| Operação humana identificada por `iss` + `sub`, com RBAC.

| `/v1/identify`
| Token de `api_clients`
| Identidade para edge/injector: retorna apenas `tenantSlug`, sem resources ou
  segredos.

| `/v1/resolve*`
| Token de `api_clients`
| Configuração server-to-server para a aplicação que usa os resources; pode
  retornar segredos descriptografados sobre TLS.
|===

Sessões guardam somente hash do token opaco, expiram por limite absoluto e idle,
podem ser revogadas imediatamente e nunca contêm token do IdP. O token CSRF é
hash-only para validação e cifrado apenas para ser devolvido à sessão same-origin.
`TENANCIT_ADMIN_TOKEN`, quando break-glass está explicitamente habilitado, é
convertido em hash durante o boot; configuração parcial falha fechado.
API clients são persistidos com hash SHA-256; o token bruto aparece uma vez.
O contrato completo está na
link:adr/0005-identidade-humana-admin-oidc-sessoes-rbac.md[ADR 0005].

Identify e resolve exigem autenticação mesmo tendo responsabilidades distintas.
O `tenantSlug` propagado como `x-tenant-id` é identidade, não uma credencial: a
aplicação deve aceitar esse header apenas de uma borda confiável e ainda usar
seu API client para resolver recursos. Tokens não devem ser propagados junto
com a request do usuário nem registrados em logs.

==== Cache e revalidação

`/v1/identify` não acessa secrets e pode devolver
`Cache-Control: private, no-cache`; seu `ETag` permite revalidar o mapeamento
hostname -> tenant com `If-None-Match`. `/v1/resolve*` devolve
`Cache-Control: private, no-store`, porque seu corpo pode conter credenciais, e
usa outro `ETag` para revalidar a configuração. Um `304` evita novo payload e
novo decrypt, mas não autoriza cache compartilhado nem torna os ETags das duas
operações intercambiáveis. Detalhes normativos estão em
<<eng-contratos-http,Contratos HTTP>>.

==== Segredos de resources

Campos marcados como `is_secret` são cifrados com AES-256-GCM. Variáveis:

[cols="1,3",options="header"]
|===
| Variável | Uso

| `TENANCIT_AES_KEY`
| Chave atual em base64, obrigatoriamente 32 bytes.

| `TENANCIT_AES_KEY_VERSION`
| Versão atual da chave. Default lógico: `1`.

| `TENANCIT_AES_KEY_V<n>`
| Entradas adicionais do keyring para decrypt durante rotação. Podem ser
  staged antes do cutover e incluem versões anteriores ou futuras à corrente.
|===

O schema guarda `key_version` em `tenant_resource_values`. O comando offline
`tenancit-rewrap` autentica todos os ciphertexts em dry-run e recriptografa por
lotes com lock, `SKIP LOCKED`, CAS e buffers apagáveis. Ele exige backup/restore
fresh, login PostgreSQL mínimo e confirmação UUID; não existe endpoint de
rotação. O procedimento completo está em
link:runbooks/aes-key-rewrap.md[Rewrap de chave AES].

O fluxo identify termina antes da montagem e do decrypt de resources. Somente
resolve e o reveal admin explícito atravessam a fronteira em que um secret passa
a existir em claro fora do armazenamento cifrado.

==== Reveal no admin

O admin endpoint mascara secrets por padrão. O painel só requisita
`?reveal=true` quando o operador aciona *Revelar segredos*. Esse reveal é uma
ação sensível: depois dele, o valor claro existe no browser enquanto a tela
estiver em uso.

==== TLS

O serviço assume TLS na borda ou no caminho interno confiável. Como consumers
recebem secrets descriptografados, deploys reais não devem expor `/v1/resolve`
por HTTP sem TLS fora de ambientes locais controlados.

==== Defesas da resposta HTTP

O servidor aplica CSP same-origin, `frame-ancestors 'none'`,
`X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`,
`Referrer-Policy: no-referrer`, `Permissions-Policy` restritiva e HSTS. O build
da SPA não exige `unsafe-eval`; `unsafe-inline` permanece limitado a styles.
HSTS só produz a proteção pretendida quando o serviço é publicado por HTTPS.
