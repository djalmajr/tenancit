[#eng-contratos-http]
=== Contratos HTTP

Todas as rotas de API usam o prefixo `/v1`. O painel SPA é servido pelo mesmo
binário e usa a API admin same-origin.

==== Admin API

Proteção normal: cookie de sessão opaco `HttpOnly` criado por Authorization
Code + PKCE no backend. Mutações e reveal também exigem origin válido e
`X-CSRF-Token`. O principal OIDC recebe permissões por role deny-by-default.
O bearer administrativo é aceito somente quando break-glass estiver habilitado
explicitamente; não é usado pela SPA e possui permissões mínimas.

Mutações críticas exigem `Idempotency-Key` UUID: `POST /v1/admin/tenants`,
`POST /v1/admin/tenants/{id}/resources`, `POST /v1/admin/api-clients` e
`POST /v1/admin/api-clients/{id}/rotate`. A chave é escopada pelo principal e
operação. Mesmo payload reproduz status/body e envia
`Idempotency-Replayed: true`; payload divergente retorna
`409 idempotency_mismatch`. Create/rotate de client preservam o mesmo envelope
cifrado por 10 minutos; tenant/resource por 24 horas. Chave ausente ou inválida
retorna `400 idempotency_key_required`.

[cols="1,2,3",options="header"]
|===
| Método | Path | Uso

| `GET`
| `/v1/auth/config`, `/v1/auth/login`, `/v1/auth/callback`, `/v1/auth/session`
| Descoberta pública do modo, início/callback OIDC e sessão atual.

| `POST`
| `/v1/auth/logout`
| Revoga imediatamente a sessão atual; exige CSRF/origin.

| `GET`, `DELETE`, `POST`
| `/v1/admin/sessions`, `/v1/admin/sessions/{id}`, `/v1/admin/sessions/revoke-principal`
| Inventário e revogação administrativa. A sessão atual não pode ser revogada
  por esses endpoints; usa logout explícito.

| `GET`, `PATCH`
| `/v1/admin/settings`
| Registry fechado de políticas runtime não secretas. `PATCH` exige
  `If-Match: "settings-{revision}"`; conflito retorna `412`.
|===

[cols="1,2,3",options="header"]
|===
| Método | Path | Uso

| `GET`
| `/v1/admin/overview`
| Métricas e cards resumidos do painel.

| `GET`
| `/v1/admin/operational-health`
| Readiness sanitizada, filas/circuitos e reports mais recentes com status
  efetivo por freshness.

| `GET`
| `/v1/admin/audit-events`, `/v1/admin/audit-health`
| Activity com filtros exatos/cursor keyset e saúde de partições/holds. Exigem
  `audit.read`; cada consulta da trilha também é auditada.

| `POST`, `GET`, `GET`
| `/v1/admin/audit-exports`, `/v1/admin/audit-exports/{id}`,
  `/v1/admin/audit-exports/{id}/download`
| Export CSV/JSONL idempotente, cifrado, expirável e download one-shot. Exige
  `audit.export`; janela máxima 31 dias e teto 100.000 eventos.

| `GET`, `POST`, `POST`
| `/v1/admin/audit-legal-holds`, `/v1/admin/audit-legal-holds`,
  `/v1/admin/audit-legal-holds/{id}/release`
| Inventário, criação e liberação auditada de legal holds; exige `audit.manage`.

| `POST`, `GET`, `GET`, `PUT`, `DELETE`
| `/v1/admin/tenants`, `/v1/admin/tenants/{id}`
| CRUD principal de tenants. `DELETE` remove o tenant e, por FK `ON DELETE CASCADE`, seus domains/resources/values (204; 404 se não existir).

| `POST`, `GET`, `PUT`, `DELETE`
| `/v1/admin/tenants/{id}/domains`
| Hostnames associados ao tenant. O `PUT` atua em `/{domainId}`, canonicaliza o hostname e preserva unicidade global.

| `POST`, `GET`, `PUT`, `DELETE`
| `/v1/admin/tenants/{id}/resources`
| Provisionamento, listagem, edição de nome/alias via `PATCH /{resourceId}`, status e remoção de resources.

| `POST`, `GET`, `PUT`
| `/v1/admin/resource-definitions`
| Catálogo de definitions.

| `POST`, `DELETE`
| `/v1/admin/resource-definitions/{id}/fields`
| Gestão de fields da definition.

| `POST`, `GET`, `PUT`
| `/v1/admin/api-clients`
| Criação, listagem e revogação de API clients.
|===

Webhooks administrativos usam `/v1/admin/webhook-targets` e
`/v1/admin/webhook-deliveries`; criação devolve signing secret somente uma vez
com `private, no-store`. Catálogo, assinatura e change feed estão em
link:webhook-events.md[Webhooks e change feed].

Agentes operacionais usam `POST /v1/operations/reports` com credencial Bearer
própria e `Idempotency-Key`; esse endpoint não aceita sessão admin nem API key de
consumo. Kinds são fechados em `backup|restore|rewrap|migration`, status em
`healthy|degraded|failed`, e reports expirados aparecem como `stale` na leitura.

Segredos na listagem admin são mascarados por padrão. A query
`?reveal=true` só deve ser usada por ação explícita de operador autenticado e
responde `Cache-Control: private, no-store`; a SPA também usa o modo fetch
`no-store` nessa request.
Corpos JSON administrativos são limitados a 1 MiB; payloads maiores recebem
`413 Request Entity Too Large`. API clients nunca expõem `key_hash`; o token
bruto aparece somente na resposta de criação e deve ser capturado naquele momento.
Dentro da janela idempotente, um retry autorizado da mesma operação recupera a
mesma resposta; a lista e os demais endpoints continuam sem expor o token.

==== Consumer API

Proteção: `Authorization: Bearer <api-client-token>`.

[source,http]
----
GET /v1/resolve?hostname=cliente.example.com
Authorization: Bearer tnc_...
----

Identidade alternativa por slug (usada por um app que já recebeu o `x-tenant-id`
e precisa resolver o próprio recurso, sem conhecer o hostname):

[source,http]
----
GET /v1/resolve?tenantId=<tenant-slug>
Authorization: Bearer tnc_...
----

Exatamente um de `hostname` ou `tenantId` é obrigatório (`400` se ambos estiverem
ausentes ou se forem enviados juntos); os dois caminhos, usados separadamente,
resolvem o mesmo tenant e produzem o mesmo `ETag`.

Resposta:

[source,json]
----
{
  "tenantSlug": "cliente",
  "resources": [
    {
      "alias": "postgres.agility",
      "definitionKey": "postgres",
      "values": {
        "host": "db.internal",
        "password": "cleartext-over-tls"
      }
    }
  ]
}
----

Hostnames são DNS case-insensitive: entrada e consulta são canonicalizadas para
ASCII minúsculo, sem espaços ou ponto final. IDNs precisam ser fornecidos em
punycode explícito.

Cache / revalidação: a resposta carrega `ETag` (forte — derivado do tenant, dos
resources ativos, das origens vinculadas e da versão de suas definitions) e `Cache-Control: private, no-store`,
pois o corpo contém credenciais em texto claro. O consumidor pode reter o
validador na própria aplicação e enviar `If-None-Match: <etag>`; quando nada mudou
o servidor responde `304 Not Modified` sem corpo e *sem redecifrar*. Qualquer
alteração em tenant, resource, valor ou field da definition muda o `ETag`.

Identidade para a borda (injector que injeta `x-tenant-id` e *nunca* toca em
credenciais): retorna só o slug do tenant, sem resources/segredos.

[source,http]
----
GET /v1/identify?hostname=cliente.example.com
Authorization: Bearer tnc_...
----

[source,json]
----
{ "tenantSlug": "cliente" }
----

Também emite `ETag` (estável — só muda quando o tenant muda) e
`Cache-Control: private, no-cache`; caches privados podem armazenar a resposta,
mas devem revalidar cada uso com `If-None-Match` (resposta `304` quando o
mapeamento não mudou). Isso evita servir a identidade anterior quando um
hostname é removido de um tenant e atribuído a outro.

Atalho por alias (o alias é único dentro do tenant):

[source,http]
----
GET /v1/resolve/{hostname}/resources/{alias}
Authorization: Bearer tnc_...
----

Diretório de tenants para consumidores com o scope `tenant:list` (identidades
apenas — slug, nome e status; nunca resources ou secrets). Pensado para pontes
de control plane que espelham o diretório (ex.: shells de plataforma):

[source,http]
----
GET /v1/tenants
Authorization: Bearer tnc_...
----

[source,json]
----
[ { "slug": "cliente", "name": "Cliente", "status": "active" } ]
----

Responde `Cache-Control: private, no-cache`; sem o scope, `403 insufficient_scope`.

Escrita de valores para consumidores com o scope `resource:write` — apenas
campos **não-secretos** de resources existentes (endereçados por slug + alias);
campos secretos respondem `403` sempre (gestão de secrets fica no console):

[source,http]
----
PATCH /v1/tenants/{slug}/resources/{alias}/values/{fieldKey}
Authorization: Bearer tnc_...
Content-Type: application/json

{ "value": "novo-valor" }
----

Responde `204`; campo desconhecido `400`; tenant/resource inexistente `404`.

Change feed cronológico para integrações que preferem pull:

[source,http]
----
GET /v1/events?cursor=<cursor-opaco>&limit=100
Authorization: Bearer tnc_...
----

Exige exclusivamente o scope `events:read`, usa paginação keyset e responde
`Cache-Control: private, no-store`. O payload contém apenas referências
versionadas e nunca valores, secrets, tokens ou hashes. O contrato detalhado,
incluindo o formato do cursor, está em link:webhook-events.md[Webhooks e change feed].

==== Erros esperados

[cols="1,3",options="header"]
|===
| Status | Situação

| `400`
| Payload inválido, id inválido, definition desconhecida/inativa ou campo
  obrigatório ausente.

| `401`
| Token admin/API ausente, inválido ou revogado.

| `404`
| Hostname/resource não encontrado no consumo, tenant inativo ou mutação
  aninhada cujo filho não pertence ao parent informado.

| `413`
| Corpo JSON administrativo maior que 1 MiB.

| `409`
| Violação de unicidade, como hostname duplicado ou segundo resource ativo do
  mesmo tipo para o tenant.

| `500`
| Erro inesperado de banco, cripto ou infraestrutura.
|===
