=== Escopo e roadmap

==== Escopo atual

* Serviço Go com API HTTP e SPA admin embutida.
* PostgreSQL como única dependência persistente.
* Migrations via goose e consultas type-safe via sqlc.
* Criptografia AES-256-GCM com `key_version`.
* Resolução por hostname canônico (case-insensitive, sem trailing dot).
* API key server-to-server para consumo.
* Token dedicado para admin.
* Dockerfile e `docker-compose.yml` para execução local/containerizada.
* Headers HTTP defensivos na SPA e na API.

==== Fora do escopo atual

* Login humano completo para o painel admin via IdP.
* Auditoria detalhada de ações administrativas.
* Rotação automática de chaves AES.
* Multi-região ou cache distribuído.
* Versionamento coexistente de definitions.

==== Trajetória recomendada

Objetivo: sair do bootstrap seguro de instância única para uma operação
multioperador auditável e com credenciais governadas, sem enfraquecer a
fronteira de secrets.

Sequência recomendada: aprovar identidade + auditoria em paralelo; introduzir o
principal/audit primitives; entregar OIDC/RBAC e auditoria por cortes; aplicar a
política de API clients antes de escalar réplicas; implementar rewrap após o
backup/restore estar validado no alvo.

Não são compromissos desta trajetória: multi-região, storage WORM/SIEM, HSM,
cache distribuído genérico ou allowlist de CIDR antes de a topologia de proxies
ser definida e testada.

==== Incrementos técnicos concluídos

* Montagem enriquecida de tenant resources sem N+1: headers e fields/values são
  carregados em queries batch, mantendo máscara/decriptação no pacote `service`.
* ETag cobre mutações de status, fields e values sem decriptar para responder 304.
* Fluxo de borda sem secrets, hard delete explícito e snippets de integração
  estão documentados e cobertos por testes.
* TanStack Query iniciou pela tela de API clients; o gate web agora inclui regras
  ESLint de hooks, typecheck e Vitest.
* Bootstrap, smoke e backup/restore locais têm runbooks validados; deploy real
  permanece dependente da escolha do alvo.
